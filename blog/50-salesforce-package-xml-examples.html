50 Real Salesforce package.xml Examples

Copy-ready manifest examples for Apex, Flows, Lightning Web Components, objects, fields, security, reports, and everyday Salesforce metadata work.

By Shubham Lashkan · Updated November 15, 2026

Generate a package.xml manifest →

A Salesforce package.xml manifest tells the Metadata API which metadata component types and members to retrieve or deploy. The <name> value must be the Metadata API type name—not simply the label shown in Setup—and each <members> value must use the component's Metadata API full name.

Before you copy an example: Component names such as Invoice__c and InvoiceService are illustrative; replace them with names from your org. Examples use Metadata API version 68.0. Use a version supported by your Salesforce org and deployment tooling. The current generator's default is 66.0; you can change its version field when generating a manifest.

How to use these examples

  1. Find the metadata type and member pattern that matches your task.
  2. Replace each sample member with the exact API/full name from your Salesforce org.
  3. Keep separate <types> blocks for separate metadata types.
  4. Validate component names, dependencies, permissions, and API-version compatibility before deploying.

50 package.xml examples

1. Retrieve every Apex class

Use the wildcard to request all Apex classes. This is useful for a broad code review or a full source retrieval.

<?xml version="1.0" encoding="UTF-8"?>
<Package xmlns="http://soap.sforce.com/2006/04/metadata">
    <types>
        <members>*</members>
        <name>ApexClass</name>
    </types>
    <version>68.0</version>
</Package>

2. Retrieve one Apex class

Replace the sample name with the Apex class API name in your org.

<?xml version="1.0" encoding="UTF-8"?>
<Package xmlns="http://soap.sforce.com/2006/04/metadata">
    <types>
        <members>InvoiceService</members>
        <name>ApexClass</name>

Important naming and retrieval notes

  • Custom fields: use ObjectApiName.FieldApiName, for example Invoice__c.External_Reference__c.
  • Validation rules and record types: qualify the component with its object, such as Invoice__c.Require_Invoice_Number.
  • Reports, dashboards, and email templates: include the folder in the member full name where required.
  • Custom metadata records: use TypeDeveloperName.RecordDeveloperName; the custom metadata type's __mdt suffix is not included in the type portion of the record member.
  • Sharing rules: the Metadata API type is SharingRules (plural), not SharingRule.
  • Profiles: use the profile metadata full name, which can differ from the profile label shown in Setup.
  • Wildcards: * is supported only for metadata types that allow wildcard retrieval. Check the Salesforce Metadata Types reference before relying on it.
